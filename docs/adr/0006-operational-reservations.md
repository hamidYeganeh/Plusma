# رزرو عملیاتی با NestJS و PostgreSQL

کاربر اجرای مرحله رزرو واقعی و استفاده از NestJS را درخواست کرده است. تعویق backend در ADR-0001 و ADR-0005 برای این بخش جایگزین می‌شود؛ نمایشگر مستقل و ownership صحنه تغییری نمی‌کنند.

`apps/api` یک modular monolith با NestJS است. ماژول مشترک `access` هویت کارکنان، session، عضویت سازمان و مجوز مکان را نگه می‌دارد. ماژول تجاری `cafe-booking` پشت interface کوچک HTTP، زمان‌بندی، ظرفیت، نگه‌داشت، تأیید، لغو و ورود مهمان را پیاده می‌کند. اتصال و lifecycle پایگاه داده در `database` قرار دارند. `packages/contracts` تنها شکل داده‌های HTTP را بین callerهای واقعی مرورگر و Nest به اشتراک می‌گذارد؛ هیچ قانون تجاری یا وابستگی به صحنه ندارد.

جایگزین استفاده از ORM و repository عمومی، SQL پارامتری و تراکنش مستقیم در implementation رزرو است. همه تغییرهای ظرفیت ابتدا همان میز را قفل می‌کنند. محدودیت exclusion در PostgreSQL هم از هم‌پوشانی بازه‌های فعال محافظت می‌کند. بازه‌ها نیمه‌باز هستند؛ پایان یک رزرو می‌تواند شروع رزرو بعدی باشد. یک میز برای هر رزرو به‌طور کامل تخصیص می‌یابد؛ نفرات دو گروه روی یک میز ترکیب نمی‌شوند.

زمان‌های مجاز و ظرفیت از دیتابیس می‌آیند؛ داده صحنه فقط برای نمایش است. پیش‌فرض قابل تغییر مکان، Asia/Tehran، ساعت ۱۰ تا ۲۳، فاصله شروع‌ها ۳۰ دقیقه، مدت حضور ۹۰ دقیقه و مهلت نگه‌داشت ۵ دقیقه است. افق رزرو ۳۰ روز است. نگه‌داشت منقضی در خواندن آزاد محسوب می‌شود و هنگام تخصیص مجدد همان میز در تراکنش expired می‌شود. ورود از ۳۰ دقیقه پیش از شروع تا پایان مجاز است. ثبت شماره تماس به معنی احراز آن با پیامک نیست.

کلید idempotency برای hold، confirm، cancel و check-in الزامی است. تغییر payload با کلید قبلی 409 می‌دهد؛ retry موفق نتیجه همان فرمان را برمی‌گرداند. توکن مهمان از راز مشترک همه replicaها و کلید نگه‌داشت مشتق می‌شود تا پاسخ گم‌شده بدون ذخیره توکن خام بازیابی شود. تنها hash آن در رزرو ذخیره می‌شود. کد پیگیری عمومی مجوز مشاهده یا لغو نیست. توکن در sessionStorage همان زبانه نگه‌داری می‌شود؛ بازیابی پس از بسته‌شدن زبانه هنوز نیازمند فلو احراز تماس در فاز بعد است.

session کارکنان opaque، hash شده در PostgreSQL و در cookie با HttpOnly و SameSite=Strict است. درخواست تغییر از مرورگر باید Origin مجاز داشته باشد. نقش owner در تمام مکان‌های سازمان خودش مجاز است؛ staff فقط مکان‌های واگذارشده را می‌بیند. شناسه tenant از body درخواست مورد اعتماد قرار نمی‌گیرد. رخداد تغییر وضعیت و عامل کارکنان ثبت می‌شوند.

این انتخاب توزیع چند replica را بدون state ضروری در حافظه ممکن می‌کند؛ قفل هر میز، نه قفل همه سازمان‌ها، contention را محدود می‌کند. worker، broker، پرداخت، صندوق، سفارش، RBAC عمومی و microservice پیشاپیش ساخته نمی‌شوند. در رشد واقعی، ظرفیت pool، زمان انتظار قفل، rate limit، نگه‌داری session و رخدادها، backup و بازیابی PostgreSQL باید با بار واقعی تنظیم شوند.

آزمون interface با HTTP واقعی Nest و PostgreSQL موقت مستقل، رزرو هم‌زمان، retry، انقضا، جداسازی مکان/سازمان و دسترسی کارکنان را پوشش می‌دهد.
