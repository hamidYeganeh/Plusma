# اصول مهندسی و معیار بازبینی

این قواعد برای هر تغییر اعمال می‌شوند. ADR دلیل انتخاب معماری را ثبت می‌کند؛ این سند معیار روزمره اجرای آن است.

## SOLID

| اصل | کاربرد در این پروژه                                                  | معیار بازبینی                                                                                |
| --- | -------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| SRP | catalog، ارائه، runtime، صحنه و UI دلایل تغییر مستقل دارند           | تغییر نام کافه به کد GPU نیاز ندارد؛ تغییر رنگ به مسیر‌یابی نیاز ندارد                       |
| OCP | کافه جدید با محتوای جدید و صحنه خودش ارائه می‌شود                    | template کپی نمی‌شود؛ با صحنه دوم interface فقط بر اساس تفاوت واقعی استخراج می‌شود           |
| LSP | هر implementation صحنه آینده باید invariants lifecycle را رعایت کند  | در آینده هر صحنه: mount، تغییر اندازه و dispose بدون اثر روی صحنه دیگر                       |
| ISP | caller به جزئیات Three دسترسی ندارد                                  | صفحه برای جابه‌جایی به یک نقطه، camera یا renderer را دست‌کاری نمی‌کند                       |
| DIP | runtime canvas و callback دریافت می‌کند؛ UI به handle آن تکیه می‌کند | runtime به router، متن و فرم وابسته نیست؛ type-only import کد GPU را وارد صفحه فهرست نمی‌کند |

LSP و OCP مجوز ساخت سلسله‌مراتب کلاس فرضی نیستند. امروز یک implementation صحنه داریم؛ contract چندصحنه‌ای هنگام نیاز واقعی تثبیت می‌شود.

## Clean Code

نام دامنه از GLOSSARY؛ متن رابط در messages؛ نام‌گذاری مشخص برای حالت، خطا و cleanup؛ پرهیز از متغیر سراسری mutable، queryهای سراسری DOM و دسترسی مرورگر هنگام import. بازبینی به رفتار واقعی توجه کند؛ کم‌کردن تعداد خط به‌تنهایی معیار کیفیت نیست.

## KISS

فعلاً catalog محلی و یک برنامه وب. بدون backend، auth، DB، container DI، CQRS، microservice یا generic repository. داده ثابت با تابع جست‌وجوی ساده خوانده می‌شود. افزودن الگو باید مسئله مشخصی را حل کند.

## DRY

توکن‌های طراحی، primitiveهای UI و محاسبات حرکت یک مرجع دارند. هر کافه fork جدا نیست. دو قطعه کد فقط به دلیل شباهت ظاهری ادغام نمی‌شوند؛ قواعد رزرو سینما و کافه تفاوت دامنه‌ای دارند.

## Separation of concerns

جریان وابستگی از route و ارائه به moduleهای رفتار است. backend آینده مالک قواعد تراکنشی می‌شود؛ canvas مرجع ظرفیت، پول یا مجوز نیست. تم رابط و نور صحنه دو concern مستقل‌اند؛ تغییر dark mode، نور روز/شب کافه را تغییر نمی‌دهد.

## آزمون و نگه‌داری

آزمون‌ها از همان interface مصرفی caller عبور کنند. برخورد، مسیرهای قابل عبور و ورودی چندلمسی در انتقال فعلی ریسک واقعی‌اند. بررسی ساخت، نوع و lint لازم است؛ تست‌های تقلیدکننده implementation یا ده‌ها helper عبوری ارزش خودکار ندارند.

## الگوهای مشروط آینده

Strategy برای تفاوت واقعی قواعد صنف‌ها؛ Adapter برای دستگاه یا ذخیره‌سازی واقعی متفاوت؛ Outbox و Idempotency برای sync؛ state machine برای رزرو/پرداخت با حالت‌های مشخص. نام الگو در مستندات به معنی پیاده‌شدنش نیست.
