# افزودن یک حوزهٔ کسب‌وکار

نمایش فضایی مشترک است؛ مدل و تجربهٔ هر حوزه در module خودش قرار می‌گیرد. مرجع تصمیم: [ADR-0005](../adr/0005-independent-spatial-module.md).

## مسیر اضافه‌کردن ملک

۱. اطلاعات ملک و آگهی را در `apps/space/modules/real-estate` تعریف کن. ملک، فایل فروش/اجاره و درخواست بازدید مفاهیم همان حوزه‌اند و از `Cafe` ارث نمی‌برند.
۲. scene adapter آن حوزه یک `SceneDefinition` از `@repo/spatial` فراهم کند: شناسه، هدف‌ها، waypoint شروع، navigation، نقشه و builder. از [fixture مسکونی](../../packages/spatial/tests/fixtures/residential-scene.ts) به‌عنوان نمونهٔ اجرایی قرارداد استفاده کن؛ fixture دادهٔ محصول نیست.
۳. در تجربهٔ ملک، هدف صحنه را به شناسهٔ اتاق وصل کن و پنل اطلاعات یا درخواست بازدید را همان‌جا باز کن. نمایشگر فقط شناسهٔ هدف را گزارش می‌کند.
۴. route عمومی فقط از interface عمومی `real-estate` استفاده کند. builder و `@repo/spatial/runtime` بعد از mount به‌شکل پویا بارگیری شوند.
۵. تغییر مدل یا آگهی نباید به ویرایش module کافه یا runtime نیاز داشته باشد. شناسهٔ اتاق و ملک از هندسه مستقل بماند؛ ارتباط آن‌ها در adapter متعلق به حوزه نگه داشته شود.

## قواعد قابل بررسی

- package مشترک از هیچ app وارد نمی‌کند؛ appها هم از app دیگر import نمی‌کنند.
- عبور از workspace از طریق exports بسته و dependency اعلام‌شده است.
- مصرف یک module از بیرون، از `index.ts` یا interfaceهای صریح ثبت‌شده در `module.json` انجام می‌شود. فایل‌های عمومی کافه `experience/index.ts`، `scenes/index.ts` و `staff/index.ts` هستند.
- importهای نسبی، alias، type import، re-export و dynamic import در `npm run check:architecture` بررسی می‌شوند؛ همین بررسی جزئی از lint ریشه است.
- scaffoldهای خالی برای صنف‌های فرضی ساخته نمی‌شوند؛ module جدید با اولین رفتار واقعی و تست interface خودش ایجاد می‌شود؛ `kind: business` در `module.json` استقلال آن از حوزه‌های دیگر را enforce می‌کند.

## زیرساخت عملیاتی در فازهای بعد

Backend اکنون با NestJS ساخته شده است: `database` و `access` مشترک‌اند و `cafe-booking` مالک رزرو کافه است. `access` هیچ جدول صنفی را نمی‌شناسد. تجربه ملک باید ماژول تجاری مستقل خودش را داشته باشد؛ زمان بازدید ملک، قرارداد فروش و سرنخ مشتری نباید از مدل میز/ظرفیت کافه به ارث برسند. قراردادهای HTTP تنها برای callerهای واقعی در `@repo/contracts` تعریف می‌شوند. قواعد، تراکنش و آزمون‌های صنف جدید در همان ماژول قرار می‌گیرند. صف پایدار، worker و object storage با مصرف واقعی افزوده می‌شوند. رزرو و جداسازی سازمان/مکان پیاده و آزموده‌اند؛ پرداخت و همگام‌سازی صندوق هنوز ساخته نشده‌اند.
