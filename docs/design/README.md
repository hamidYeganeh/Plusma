# بلوپرینت

## وضع فعلی

یک برنامه فعال داریم: `apps/space`. Next.js صفحات عمومی را می‌سازد؛ catalog محلی داده عمومی کافه را تأمین می‌کند. Three.js فقط در مسیر نمایش کافه و پس از mount مرورگر بارگیری می‌شود. رزرو عملیاتی و backend وجود ندارند؛ پیش‌نمایش رزرو کاملاً محلی است.

```text
صفحه فهرست / صفحه cafe/[slug]
         │
         ├── catalog: نام، slug، معرفی، preview، شناسه صحنه، خلاصه میزها
         │
         └── CafeExplorer: ارائه، وضعیت رابط و پیام‌ها
                    │
                    ├── packages/ui: primitiveهای مشترک
                    ├── next-intl: متن و زبان
                    ├── next-themes: تم رابط
                    └── runtime: دوربین، ورودی، حرکت و lifecycle
                              └── scenes/barg: هندسه، بافت و چیدمان
```

## مسئولیت‌ها و جهت وابستگی

- route: حل slug، metadata و not-found؛ بدون هندسه و رویداد مرورگر.
- catalog: داده عمومی؛ بدون renderer، fetch و وضعیت کاربر.
- نمایش: ترکیب کنترل‌ها و نمایش وضعیت؛ بدون محاسبه برخورد و دست‌کاری دوربین.
- runtime: مالک loop، ورودی، کنترل حرکت، اندازه canvas و cleanup؛ بدون متن فارسی، رزرو و شبکه.
- صحنه برگ: هندسه و نور؛ بدون آگاهی از Next، فرم و حساب کاربر.
- UI: primitive و variantهای بصری؛ بدون import از apps.
- ترجمه: `messages/fa.json`؛ اطلاعات نام و معرفی کافه محتوای catalog هستند.

هیچ app از app دیگر import نمی‌کند. module دارای interface عمومی کوچک و implementation داخلی است. کوچک بودن تابع به‌تنهایی نقص معماری نیست؛ deletion test باید نشان دهد حذف module پیچیدگی را بین callerها پخش می‌کند.

## الگوهای استفاده‌شده

Composition برای ترکیب primitiveهای UI؛ Facade برای پنهان‌کردن چرخه عمر Three؛ constructor/factory ساده برای ساخت صحنه؛ configuration-driven rendering برای اطلاعات کافه؛ Observerهای مرورگر برای resize و lifecycle. DI در interface runtime به شکل canvas و callbackهای ورودی است، بدون container سراسری.

یک صحنه واقعی داریم؛ registry پیچیده، repository abstraction، event bus و adapter شبکه ساختگی اضافه نشده‌اند. هنگام ورود صحنه دوم، تفاوت‌های واقعی در layout، waypoints و builder مبنای استخراج interface مشترک خواهند بود.

## lifecycle

بعد از mount، import پویا با پرچم cancellation انجام می‌شود. خروج، loop را متوقف می‌کند، listenerها و observerها را حذف می‌کند و منابع هندسی، بافت، نور، reflection و renderer را آزاد می‌کند. وضعیت حرکت در blur و hidden پاک می‌شود. راهنما ورودی صحنه را متوقف می‌کند.

## انتخاب میز و کیفیت رندر

`cafes/data/barg-tables.js` مرجع چیدمان و ظرفیت میزهاست؛ catalog فقط خلاصه عمومی را به رابط می‌دهد. `TablePanel` مسئول انتخاب و نمایش اطلاعات است. runtime انتخاب را روی هندسه و نقشه برجسته می‌کند؛ `table-navigation.js` مسیر ایستادن کنار میز را از قواعد برخورد می‌گیرد. هیچ وضعیت رزرو یا موجودی به صحنه اضافه نشده است.

`render-quality.js` بودجه اولیه را بر اساس عرض، اشاره‌گر لمسی و قابلیت‌های اعلام‌شده دستگاه تعیین می‌کند. موبایل از reflection pass صرف‌نظر می‌کند؛ دستگاه محدود بافت کوچک‌تر، برگ کمتر و سقف هدف ۳۰ فریم دارد. پس از گرم‌شدن، نمونه ۹۰ فریم فعال با میانه بیش از ۳۸ms یک بار DPR و shadow/reflection را کاهش می‌دهد. این برآورد جای benchmark سخت‌افزار واقعی را نمی‌گیرد.

در صفحه پنهان، loop متوقف و ورودی‌ها پاک می‌شوند. در راهنما/صفحه ورود، پس از redraw موردنیاز loop می‌ایستد. تغییر نور زمان کوتاهی برای همگرایی نور رندر می‌کند. بازگشت و resize دوباره رندر را فعال می‌کنند.

## ساختار هدف آینده — هنوز پیاده نشده

`space` برای مهمان، `console` برای کارکنان، یک `api` با moduleهای داخلی برای قواعد و تراکنش‌ها؛ `desk` برای صندوق محلی و `worker` برای کار پایدار پس‌زمینه. PostgreSQL و object storage هنگام ورود داده عملیاتی بررسی می‌شوند. تصمیم آینده جای الزام فعلی به داده محلی را نمی‌گیرد.

هسته مشترک مکان/صحنه با قواعد رزرو کافه یکی نیست؛ ملک، تالار و سینما منو و ظرفیت میز کافه را به ارث نمی‌برند. این توپولوژی آینده پیشنهادی است و ADR پذیرفته‌شده اجرای آن وجود ندارد.

## اکشن رزرو در دمو

`modules/reservations` مسئول انتخاب زمان نمونه، محدودیت تعداد مهمان بر اساس ظرفیت میز و مرور خلاصه است. `TablePanel` فقط میز و نام کافه را به این جریان می‌دهد. canvas هنگام باز بودن dialog متوقف می‌شود؛ قواعد رزرو وارد runtime یا هندسه نشده‌اند. هیچ مشخصات شخصی، ذخیره‌سازی، درخواست شبکه، کد پیگیری یا ادعای ظرفیت آزاد وجود ندارد. روزها بر اساس نیمه‌شب تهران و با نمایش تقویم فارسی ساخته می‌شوند؛ ساعت‌ها داده نمایشی‌اند، نه ساعت کاری کافه.

اشیای مرجع عکاسی در `scenes/barg/reference-objects.js` هندسه می‌سازند و از UI بی‌خبرند. مالک صحنه منابع آن‌ها را همراه سایر منابع ثبت و آزاد می‌کند. توری صندلی‌ها هنگام batching به LineSegments مشترک تبدیل می‌شود تا تعداد صندلی‌ها به همان تعداد draw call اضافه نکند. محل موانع اصلی در layout مرجع مشترک رندر و برخورد است.

## بازبینی عکس‌های برگ

یازده عکس تازه ارسالی کاربر از روز و شب، مرجع شکل و جنس مبلمان و جزئیات شدند: صندلی توری مشکی و نشیمن تیره، میز چوب ضخیم، حوض سنگ تیره، چوب‌های توخالی و شعله آبی شب، گلدان‌های سفالی و جعبه جلوی حوض، درخت با آویز و نخ آبی/فیروزه‌ای، نمای شیشه‌ای ورودی و پاف‌های طرح‌دار. ابعاد از عکس تخمین زده شده‌اند و نقشه‌برداری دقیق ادعا نمی‌شود. نوشته‌های روی استوری‌ها به عنوان دستور یا ساعت کاری معتبر استفاده نشده‌اند؛ عکس‌های دارای افراد نیز در public کپی نشده‌اند.

اکشن رزرو از همان Button، Dialog، ToggleGroup، Field و Alert کیت موجود ساخته شده است. 12ui برای ساخت مرجع جدید امتحان شد؛ درخواست شبکه ابتدا شکست خورد و بررسی خودکار مجوز، اجرای میزبانی‌شده را به دلیل ارسال تصویر محلی و احتمال مصرف اسلات پولی رد کرد. هیچ خروجی تولیدشده یا تأیید انطباق 12ui ادعا نمی‌شود؛ این مرحله کنار گذاشته شد و پنل محدود با زبان بصری موجود ترکیب شد.
